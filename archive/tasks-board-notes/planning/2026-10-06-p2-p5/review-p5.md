# Review of the P5 plan (the macOS Quick Action)

Plan: docs/mastermind/plans/2026-10-06-tasks-board-phase5-os-menu.md (3,205 lines, Tasks 0-8, 13 Rulings). Line numbers (L) are that file's.

### Verdict

**Needs fixes.** No Critical finding, two Important (a rule with no failing test; an isolation guarantee that rests on an unchecked neighbour helper), sixteen Minor. The design is sound, the templates match Apple's own bundles, and the script resists every hostile input tried. The empty `NSRequiredContext` the plan calls "not verified" (L42) is Apple's documented practice (M10).

Short answers to the lead's questions:

- **(a) The script.** No injection path. Rendered from the plan's three templates (a Python mirror of the Go code) and run under macOS `/bin/sh` (bash 3.2.57) and `/bin/dash` against stub programs in a folder whose name holds a quote and a space: 16 of 16 scenarios pass on each. They are: hostile selection, profile name and app name (`$(...)`, backticks, `;`, `|`, quotes, backslash, NUL, 0xff, a bidi override); a profile id starting with `-` (`--profile=-x` stays one argument); a 5 MB selection when the CLI stops at 1 MiB; a two-line refusal (only the last line is shown); CLI missing; osascript missing; a silent failure (default reason); a CLI that never reads stdin. The writer is never killed in any of them. `osascript` passes trailing arguments to `on run argv` as data (an injected AppleScript string came back verbatim) and the handler compiles. CLI missing and profile deleted exit non-zero with a visible reason; a locked database is a CLI error after the 5 s busy timeout (spec 3), shown as "Not added: ..." with the selection lost and no retry.
- **(b) CLI invocation.** Nothing the plan uses is missing. `--db-path` and `--profile` are root persistent flags (root.go L57, L65); P1's `task add` has `--stdin`, `--source`, `--app`; a non-agent's `--source os` becomes a Capture actor named `os`; an agent context gets `an agent's tasks are agent tasks: source "os" is for captures` (store.go L268), the substring Task 6 pins; `Store.Profile` returns an `ErrInvalid` for an unknown id and `tasks.Profile` has `id`/`name` tags; `withJSONErrors` does not recurse (automation.go L56-62), so wrapping the `os` children once in `newTaskOSCmd` prints one document; `initDB` writes the resolved active profile into the config it is given (root.go L220-226), which `withTaskStore` relies on; the root `PersistentPreRun` does not resolve `--profile`, so `uninstall --profile <deleted id>` reaches its code; main prints a failed command's error as one plain stderr line (main.go L99), so "last line" is the error.
- **(c) Templates against Apple's.** `/System/Library/Services/Show Map.workflow` and `Add to Music as a Spoken Track.workflow` (a plain text service) compared key by key: the plan's `document.wflow` is identical to Show Map's except the script, `shell` (Show Map `/bin/bash`; the plan's `/bin/sh` is the action's own default value), three UUIDs (made up, harmless), the omitted window `state`, and two `workflowMetaData` values that match the plain-text sibling instead. The plan's `Info.plist` equals that sibling plus the per-profile identifier and names, the three marker keys, and `NSRequiredContext = {}`, which Apple documents (M10). Nothing is invented. Both rendered files pass `plutil -lint` (a hostile profile name included); `plutil -extract` returns the menu item and the script byte-identical to what was rendered; `pbs -read_bundle` prints `default = "..."; NSMessage = runWorkflowAsService; "public.utf8-plain-text"`, the strings Task 5 asserts. `plutil` use is confined to `_darwin_test.go` files (`//go:build darwin`, skipped when `/usr/bin/plutil` is missing) and to the macOS-only smoke script.
- **(d) The installer.** Idempotence, the stale rewrite, `--force`, the marker, uninstall limited to managed bundles and the case-insensitive rename all check out on a desk run of the code and tests (the rename case takes the `os.SameFile` path on this Mac's disk and the older-folder path on Linux). Nothing in the tests, the smoke script or a default run writes the real `~/Library/Services` today, but one test relies on a neighbour's helper to guarantee it (I2). Gaps: M4, M8.
- **(e) Rulings 6 and 7.** Both sound; see the table. Ruling 7 goes beyond D7 and the operator list in spec 7, so the spec needs more amending than the plan's one bullet, and the user should confirm it (Question 1).
- **(f) Cross-OS.** By desk check, no production file is build-tagged; the darwin-only files are `_darwin_test.go` with `//go:build darwin`; `cmd/monoagentcli` uses a runtime check; every import is used; `strings.ContainsFunc` needs Go 1.21 and go.mod says 1.26. Gaps in the gates: M1.
- **(g) The darwin checks.** `plutil` and `pbs -read_bundle` only read: `~/Library/Preferences/pbs.plist` keeps its mtime across a `-read_bundle` call, and `-read_bundle` of a missing path exits 0 with an empty list (so only the content assertions make Task 5's test meaningful, and they are there). `automator` is not read-only: it executes the stub-driven shell script under the user's account with the real HOME and starts Automator's runner; the workflow sits in the test's temp folder, so it cannot write the Services folder, but "cannot touch the session" is too strong; "bounded to the temp folder" is accurate. It was not run.
- **(h) The PR text.** Honest on what only the user's Mac can say (L3195), incomplete on what the plan itself could not check (M16).

Not verifiable here: that macOS lists the item, whether notifications show, any `automator` run (its usage says `-i` treats each newline-terminated line as one item), that Automator loads this exact bundle.

### Critical and Important findings

Critical: none.

**I1. The success-path drain has no test that fails without it (script L709; Task 2 tests L624-655; Review Focus 3 L59; mutation table L3138).**
What: P1's `task add --stdin` reads at most 1 MiB and returns (P1 plan L4020, L4221). With a longer selection the CLI succeeds with the rest unread, and the second `cat >/dev/null 2>&1` (L709) keeps the writer from a closed pipe. The only drain test sets up two failures (L625-628), and the stub CLI always reads everything (L414). Mutation 5 (L3138) removes the `fail()` copy (L688); nothing removes L709.
Why it matters: a rule with no failing test (brief class 7), and the real case is a pasted log over 1 MiB: Automator's writer may meet EPIPE after the task was added and report the action as failed, so the user retries and files it twice. The script as written handles it (5 MB selection, CLI stopping at 1 MiB: writer and script exit 0 under both shells); only the pin is missing.
Fix: a stub mode that reads 1 MiB and exits 0 (`head -c 1048576 > "$d/stdin"`), and a new case or test (`TestTheScriptDrainsTheRestOfALargeSelectionAfterAnAdd`) expecting exit 0 and no writer error. The selection it writes must be well over 1 MiB plus a pipe buffer, about 3 MB: the existing drain test writes 500,000 bytes (L643), which a 1 MiB reader would swallow whole, so the test would still pass with L709 deleted. Add a mutation row that deletes the second `cat`; the two `cat` lines are identical text, so the executor must edit by context.

**I2. The one test that installs into the Services folder depends on a helper it never checks, and on `HOME` alone (Task 6 `newTaskOSTest` L2203-2214, `TestTaskOSRefreshesTheRealServicesFolderOnly` L2385-2412, `taskOSDir` L2633-2643; Task 0 L80-114).**
What: `install` and `uninstall` without `--dest` write under `os.UserHomeDir()/Library/Services`. That is safe only because P1's `newTaskTestDB` calls `t.Setenv("HOME", t.TempDir())` (P1 plan L3818). Task 0 does not grep for it, `newTaskOSTest` does not set HOME itself, and the assertion (L2389-2393) derives its expected path from the same `os.UserHomeDir()`, so it would pass after writing into the real folder. On Windows `os.UserHomeDir` reads `USERPROFILE`, `t.Setenv("HOME")` does nothing, and the test forces `taskOSGOOS = "darwin"` (L2210): a developer running the package there would write `%USERPROFILE%\Library\Services\...`.
Why it matters: this is the lead's first requirement for the phase, and today it rests on a neighbour's helper staying as it is.
Fix: in `newTaskOSTest` do `home := t.TempDir()`, `t.Setenv("HOME", home)`, `t.Setenv("USERPROFILE", home)`, and `t.Fatalf` unless `os.UserHomeDir()` returns `home`, before any install; compare `got.Path` with `filepath.Join(home, "Library", "Services", ...)` built from that `home`; add `grep -n 'Setenv("HOME"' cmd/monoagentcli/task_test.go` to Task 0. The smoke script is safe: every `os` command passes `--dest`, `plutil` and `pbs -read_bundle` read files under `$TMP`, and the CLI runs under `env -i HOME=$TMP/home`.

### Minor findings

- **M1. Spec 14's gates are only partly in Task 8 (L3105-3112, L3122-3124), and Ruling 13 (L51) names only the full suite.** `cmd/monoagentcli` is not run with `-race` (the new tests mutate package variables: run `-race -run 'TestTaskOS|TestTheMenus|TestEveryTaskOS|TestRefTasks'`); no `go vet -tags nosocial`; no `GOOS=windows go build`. Add them or list them in the Ruling.
- **M2. The automator test input (L2121) should end with a newline.** `automator` says each newline-terminated line is one input item; an unterminated last line may be dropped, and the test's `second < first` check would then fail for a reason that is not the workflow's.
- **M3. Shared-file anchors collide with P3 and P4.** AGENTS.md L3047 is the insertion point P3 (L5058) and P4 (L3566) also use; SECURITY.md L3055 appends after the bullet P4 replaces (P4 L3575, whose replacement starts `- **No new network surface.**` with the full stop inside the bold); CHANGELOG L3063 is top-of-Added like every phase. Resolution on rebase is trivial, but give P5 anchors of its own where possible: AGENTS.md after P1's bash block (before "A claim is a lease"), SECURITY.md after the "Text is cleaned on the way in" bullet.
- **M4. `status` judges a menu against the database of the command that asks, not the menu's own (L2817-2840), and `install` treats a bundle as "this profile's menu" by profile id alone.** Every database's first profile is `default`, so an install run with another `--db-path` silently rebinds the existing menu to that database, and `status` against another database reads a menu as `profile_gone` or stale. Record the database in a marker key (`MonoAgentTasksDB`) and use it in both places.
- **M5. `--db-path` is always pinned as an absolute path (Ruling 1 L39, `taskOSMenuSpec` L2647-2653).** After the home folder moves or the user name changes the menu breaks, where a default-path menu would not (`status` does flag it as stale). Consider leaving the flag out when the database is the default `~/.monoagent/monoagent.db`.
- **M6. `install` does not print which monoagentcli the menu will run (L2743-2762, JSON L2730-2732).** A menu installed from a dev binary in a worktree is noticed only when it goes stale. Print the CLI path and add `cli` to the JSON.
- **M7. A profile name holding U+FFFE or U+FFFF makes a menu the plan's own reader cannot read.** `plutil -lint` accepts those characters, but Go's `encoding/xml` (used by `topLevelStrings`, L1931-1966, and the tests' `parsePlist`) refuses them by the standard library's rule, and the marker keys come after `CFBundleName` in the template, so `status` and `uninstall` would not find the bundle. `cleanName` (L287-304) removes neither. Strip noncharacters there (the same treatment as the hidden set) and add `"a\U0000FFFEb"` to `TestMenuNameCleansTheProfileName`.
- **M8. `write` replaces non-atomically (L1852, L1855).** A failure between `RemoveAll(target)` and `Rename` loses the old menu; a crash leaves `.monoagent-menu-*` folders in the Services folder that nothing cleans. Rename the old bundle aside first and restore it on failure; let `uninstall` sweep leftover temp folders.
- **M9. Test hygiene.** `TestListFindsOnlyManagedBundles` calls `os.Symlink` with `t.Fatal` (L1648), which fails unprivileged on Windows: skip on error. Mutation 5 (L3138) names a line that occurs twice (L688, L709).
- **M10. Ruling 4 (L42), L1132 and Task 5 Step 4 (L2153-2155) are loose, and one claim in them is checkable.** (i) Apple's Services Properties page says of `NSRequiredContext`: "Always include this property, even when you do not require any filtering (in which case you specify an empty dictionary as the value). Otherwise the system registers your service, but does not automatically present it in the Services menu." Cite it in Ruling 4 instead of "reported, not verified"; the template needs no change. (ii) Show Map runs `/bin/bash`, not `/bin/sh`. (iii) Apple's system services keep `document.wflow` in `Contents/Resources/` (with `version.plist`), while Automator-saved workflows (`/Library/Application Support/Apple/Automator/Workflows/*.workflow`) and three third-party Quick Actions already in the user's `~/Library/Services` keep it at `Contents/document.wflow` with only `Info.plist` beside it, and `pbs -dump_cache` lists those as registered. So the plan's default layout is the evidenced one for a third-party bundle: say so in Ruling 4, so the executor does not flip `DocumentPath` on an automator failure that is not about the path, and drop the conditional sentence in the spec bullet (L3071) unless it fires.
- **M11. `ref tasks` (L3024-3038) does not say that `task os install` and `uninstall` are the operator's.** An agent reading it will try and be refused; add one line. P1's refusal text ends "or in the app" (P1 plan L4152), but the app has no install button.
- **M12. Unlisted choices.** The JSON shapes of install, status and uninstall (L2179), `--force` (in the spec's prose, not its command line), `status`'s `why`, and the script's exit 1 for a missing CLI are decisions the spec does not state: add one Ruling line.
- **M13. `hidden` is a copy of P1's (names.go L274-282, clean.go L20-28) and its test covers one rune per range (L151-169).** Add range ends and a neighbour outside each (E0000, E007F, E0080; 202A, 2029, 202F; 2069, 206A, 2065; FEFF, FEFE) so a typo in the copy fails, as P1's own tests do.
- **M14. Tie the stub's error text to the real CLI.** `TestARefusalIsShownAndPassedOn` (L594) uses an assumed line. In Task 6 add a case: insert and delete a profile by SQL, run the menu's exact arguments (`add --stdin --source os --app=Safari`) with that id, expect exit 3, the error `initializing database: profile "gone-id" not found (checked both id and name)`, and no task filed.
- **M15. Review Focus 4 (L60) says the menu is "no way round the agent limit".** That holds for invocations that keep the environment (the script run by an agent, `automator`). An agent that drives the Services menu through the GUI gets a runner without markers and files Inbox captures. The SECURITY bullet (L3058) already says "this does not stop an agent that deliberately clears its environment": use the same words in Review Focus 4. The human gate still holds.
- **M16. The PR list (L3195) omits what the plan could not check itself:** `/bin/sh` where Apple's Show Map uses bash, the `Contents/document.wflow` layout, the macOS version tested (Darwin 27 here), that `automator` is not the Services path (said in Task 5 L1996, not carried to the PR), that a successful capture shows nothing at all when notifications are off, and that the item may be listed only after the one-time enable.
