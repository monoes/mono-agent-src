**I-1 [Important] A storage read error empties the outbox** (plan L1173-1180, L1206-1221, L1237-1254; Task 3 `task_outbox.js`).
`read()` catches every storage error and returns `[]`. `enqueue` then writes `list.concat([entry])`, so one failed `get` replaces up to 199 waiting tasks with the new one. `fail` does the same (`current` and `failed` are both `[]`) and writes `[KEY]: []` plus a one-line failures list. This component's only promise is "never lost" (spec 11.3).
Fix, in two parts, because a plain "make `read` throw" breaks captures: `MonoCaptureQueue.paintBadge` (Task 4 Step 5) awaits `MonoTaskOutbox.count` and `failedCount`, and `capture_actions.js` awaits `paintBadge` outside any `catch` at L188 (`finish`, right after the capture was delivered or queued), L271 (batch end, try/finally only), L329, L334 and L339 (queue actions). A throwing count would report a capture that succeeded as failed. So: `count` and `failedCount` stay tolerant (return 0 on error, as `capture_queue.js`'s own `list` does); the read-modify-write paths (`enqueue`, `remove`, `fail`, `dismiss`) use a separate reader that throws. `enqueue` answers `{queued: false, reason: "could not read the waiting tasks: ..."}`; `remove`, `fail` and `dismiss` propagate, and `flushOnce` already treats a throw as "stopped, keep the entry". Tests in `task_outbox.test.mjs`: a storage whose `get` throws once leaves `storage.data` untouched after `enqueue`, `fail` and `remove`, and `O.count(s)` returns 0 without throwing. The current code passes every existing test with the bug present.

**I-2 [Important] The security text promises more than a closed root plus `isTrusted` delivers** (plan L78, L2789-2799 header comment, L3578 SECURITY.md, L3586 CHANGELOG, spec D22).

The design is acceptable; the sentences "a web page can neither open it under the pointer nor press its buttons" (SECURITY.md) and "so a web page can no longer press its buttons" (CHANGELOG) are not.
Fix (required): in all four places say what is true: a page script can no longer open the panel with a made-up event or click its buttons with a made-up event; a click the person makes on a panel the page moved or covered is still theirs and creates only an Inbox task. ### Answers to the dispatch's questions (a) to (h)

**(a) The Go adapter.** `chromeCapture = tasks.Actor{Kind: tasks.Capture, Name: "chrome"}` with `SourceKind: chrome` satisfies P1 rule 4 (`sourceKindFor` accepts it, the event actor is `chrome`) and never reads the environment. A page capture passes `Title` itself (page title, else `addressOf`, which drops user-info) and `Add` takes none from `SourceTitle`. `Ready` is never set and `Add` refuses it for a non-human anyway. The replay lookup runs before the limit check in `Add` (`store.go:303-313`), so a full board still answers a resend. Mapping: `ErrInvalid` to `invalid_input`, `ErrLimit` to `limit`, anything else to `internal` (the dispatcher turns an expired deadline into `timeout`). Against `request.go`: `Request.String` trims and returns `""` for a non-string, so the "blank" and "not a string" profile cases in the Go tests hold; handlers run off the read loop with a 20 s deadline and eight in flight. Risks: M-2 and M-7; and a future store refusal that is permanent (for example an `ErrOperatorOnly` path) would arrive as `internal` and be retried every minute for ever; consider mapping any other `tasks.Err*` to `invalid_input`.

**(b) Lost or duplicated tasks.** Worker killed mid-flush, reply lost, daemon restart, `timeout`: the entry stays, the resend carries the stored `client_id`, `Add` returns the existing task with `created:false`, and the extension removes the entry. The unique index on `(profile_id, client_id)` plus `BEGIN IMMEDIATE` makes two concurrent replays safe. Two browsers have two outboxes and distinct UUID ids and share no state. The flush guard (`flushing` and `again`) keeps one request in flight; "two flushes at once" fails without it. A `remove()` that fails after a successful create leaves the task queued and the person is told "will sync" for a filed task (harmless, resolves on the next flush). What can lose a task: I-1 only. What is not pinned: the stable id (I-3).

**(c) Extension security, entry point by entry point.**
- Context menu: browser UI, not scriptable; the selection text is read as data.
- Keyboard shortcut: browser UI; a page can pre-select text, so a key press with a page-made selection adds what the page chose (an Inbox task, same gate).
- Side panel box: an extension page; the manifest has no `web_accessible_resources`, so a page cannot embed it.
- Highlight panel button: no script-driven press (closed root, `isTrusted`); the residual is a baited or covered real click (I-2).
- No page-controlled text reaches `innerHTML`: the plan's JS has no `innerHTML`, `insertAdjacentHTML` or `eval`; the toast, the result line and the failures line use `textContent`.
- A hostile page cannot read the profile list: no reply path reaches it except the toast line that names one profile after a click the person made (M-16).
- A page cannot reach `chrome.runtime.sendMessage` at all (see M-1), so the sender checks are defence in depth plus one misclassification, not a gap a page can use.
- Precedents: `recorder_picker.js` (closed root, `!e.isTrusted` return) is followed; `recorder_wiring.js` (sender checks) is not (M-1).

**(d) Profile and `unavailable`.** The store validates the profile inside the transaction (`profileOf`), so a deleted profile gives `invalid_input` and is dropped and reported, never filed elsewhere (the Go test and two JS tests cover it).
