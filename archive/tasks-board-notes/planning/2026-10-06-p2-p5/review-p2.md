**I1. The skill-versus-CLI test cannot see a misspelled or renamed subcommand (Task 8, plan lines 3520-3550; Review Focus 5; mutation 13 at 4010).**
What is wrong: `Command.Find` (cobra v1.10.2, `command.go:757-779`, `args.go:28-39`) returns the group and a nil error for an unknown word under a non-root command; `legacyArgs` raises "unknown command" only at the root. The test's check `err != nil || cmd == root` (3529) therefore flags only an unknown top-level command. A skill line `monoagentcli --profile <profile-id> task shw 12` finds `task`, passes the name check, and passes the flag check (`--profile` is inherited), so the test stays green. A renamed `show`, `next`, `finish` or `release` is exactly the failure Review Focus 5 names. Mutation 13 (`--result` to `--outcome`) is caught only because `task` happens not to have that flag; a rename of a subcommand that has no flag of its own is not.
Fix: after `Find`, fail when `cmd.HasSubCommands()` ("names a command group, not a command") and require `cmd.CommandPath()` to be `monoagentcli task <leaf>` or `monoagentcli mcp`. Add a mutation row: `show` to `shw` in the skill. Flags that appear only in prose (`--lease 2h` at 3684, `--json` at 3690) are never looked up either: scan the skill's inline code spans too, or put `--lease 2h` in the code block. The test does run against the real tree (`newRootCmd()`) and will keep passing when P5 adds `task os ...`: nothing enumerates commands.

### Questions that need the user

1. **Skill layout (C1).** Claude Code loads `~/.claude/skills/<name>/SKILL.md` only; the two monoagent skills installed flat today are not in this session's skill list. Install the tasks skill as `monoagent-tasks/SKILL.md` (recommended; a few lines in `init.go`, and it would let the two older skills be moved the same way later), keep it flat knowing it is inert, or drop it? This amends D3 and §17 point 4.
2. **A restarted MCP server orphans its claims (D18).** The suffix is random per process, so after a restart (Claude Code reconnects, a crash) the agent is a new claimant: it cannot comment on, finish or release its own task until the 30-minute lease runs out, and its own claim attempt is refused as `claimed` by its old name. Accept this and say so in `task_claim`'s description (recommended), or persist a per-session id?
3. **History is unbounded for state changes (§4.4).** Only comments stop at 500 events; claim, release, finish are "always recorded". An agent that claims and releases the only Ready task in a loop grows the history and bumps the board revision without limit, and MCP makes such a loop likelier. Add a cap on a task's total events (for example 2,000, after which a claim is refused with `limit`) or accept it? This is a P1 store rule.
4. **Inbox text by id.** `Store.Get` has no actor, so an agent can read any Inbox task, the place where unreviewed captured text sits, by guessing its integer id; `task_list` shows Inbox only when named (§5.1). Is reading by id intended (§4.1 line 92 says agents "never see it unless they ask for it by name")? If not, P1 needs an actor-aware `Get`, and P2 a test.
