## Lessons from executing P1 (apply them; each cost a review round)

1. Tests that pass on any error prove little: pin the error text or code. Every rule needs a test that fails when the rule is removed; think of the mutation while you write the test. Test the boundary values (exactly the limit, one over).
2. Invisible or look-alike characters in code (bidi controls, zero-width, tag characters, BOM, replacement character) must be written as Go or JS escapes. The write tool turns four-digit escapes (backslash, u, four hex digits) into raw characters in files: write them in the eight-digit form (`\U0000202e`) or as `\x` bytes in Go, and tell the executor to run `grep -nP '[^\x00-\x7F]' <file>` after writing any such file. Never write an invisible character literally into the plan.
3. A hook refuses a Write whose content looks like an API key (the letters `sk-` followed by 20 or more key characters), and a Bash command containing destructive SQL or `rm -r`. Do not use such strings in the plan text, and do not give the plan a file name containing `task-` or `sk-`. Test SQL goes in test files, never in a Bash step.
4. In SQLite a TEXT primary key accepts NULL unless the column says NOT NULL. Foreign keys are on in the app's connections.
5. The Bash tool in worktree sessions refuses compound git commands, `git -C`, and heredocs: plan commits as two separate steps (`git add <files>`, then `git commit -m <subject> -m <trailer>`), and file writing as the Write/Edit tools.
6. A reviewer reads only the diff and the brief: every fact an executor needs (names from earlier tasks, exact expected output) belongs in the task's own text. A task's Interfaces block is how it learns its neighbours' names.
7. Chosen behaviour that the spec does not state is a Ruling; list it. Do not leave the executor to guess.
