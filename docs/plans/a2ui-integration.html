A2UI for chat, missions and human-in-the-loop

Let agents answer with real, interactive UI (approval cards, choice questions, forms, live mission progress) instead of only markdown. Google's A2UI protocol gives us the wire format. Our existing event journal gives us the transport.

Prepared 2026-11-22 from the A2UI spec (v1.0 current, v0.9.1 prior) and a read of this repo. Nothing has been implemented.

01The short version

What A2UI is

A JSON protocol where an agent describes a UI (a flat list of components plus a data model). The client renders it with its own trusted components. The agent never sends HTML, CSS or script.

Why it fits us

Our chat already runs on a typed, journaled, replayable event stream. A2UI messages become one more event type. The "UI calls the CLI" rule holds: button clicks resolve into the CLI commands we already have.

What it costs

A Go-side validator and catalog, a React renderer for the desktop, a separate vanilla renderer for the extension side panel, and an action return path. No runner (monomind) change is needed.

Recommendation: build it, starting with HIL approvals in the desktop chat (smallest, highest value, lowest risk), then missions, then the extension. Target A2UI v1.0 with our own small catalog, not the full basic catalog.

03Where it plugs into mono-agent

Today assistant output is markdown text (assistant.delta), and the only interactive pieces are hand-built cards. A2UI replaces that ad-hoc card work with one general channel.

Key design decisions in that picture

toolEmission via a caller tool

Agents call ui_render exactly as the lead calls mission_propose (internal/dynorg/mission_tools_plan.go). No runner change, no new event type in monomind, works for coder/dynorg chats today.

journalOne new event type

ui.surface in internal/ai/chatevents/event.go holds the raw A2UI messages. The envelope already tolerates unknown types, so old clients ignore it and replay by seq rebuilds the surface.

returnReuse the answer path

Actions travel through chat turn answer / ai_chat_answers, which the conductor already polls. The payload becomes JSON instead of free text. Workflow HIL buttons go straight to hil approve|reject.

trustTwo kinds of surface

System surfaces are generated by our code from a real HIL or mission record. Agent surfaces are authored by the model. Risky approvals only ever use system surfaces, so a model cannot forge an "Approve" button.

06Security model

catalogAllow-list only

Our catalog registers ~10 components. Anything else fails validation. No URLs fetched by the renderer, no HTML, no script.

actionsServer re-checks

An action must name a live surface and an allowed action name for that surface kind. Approvals resolve against the real HIL id, never against values the model supplied.

limitsBounded and redacted

Reuse RedactAndBoundJSON; cap components per surface, depth, text length and surfaces per turn. URL fields go through the existing isAllowedURL gate.

Prompt-injection angle. Extension chats read untrusted web pages. A page could try to make the agent render a fake "Approve" card. Mitigation: agent surfaces cannot use the approval action names, and the risky-send approval surface is only ever generated from a real HIL record.

07Build plan

Each phase ships behind a flag and ends with a verifiable result. Per repo rules: tests alongside code, work from a scratch HOME, proofs must not touch the live bridge.

P0
Spike: protocol core in Go ~3 days
  • internal/a2ui: v1.0 message types, parser, validator against our catalog schema, size and depth caps
  • Check community a2ui-go for reuse; otherwise port the conformance fixtures (conformance/core, conformance/agent)
  • Add ui.surface to chatevents, journal it, ignore it in clients
Verify: conformance fixtures pass; unknown-type replay test; a revert-proof test for the caps.
P1
Desktop renderer + ui_render tool ~1 week
  • React renderer (official @a2ui/react v1.0 core if it fits Vite and React 19; else a thin own renderer) with a NEXUS-styled catalog
  • Reducer case in chatReducer.js; surface lives in the timeline, survives reload via replay
  • ui_render tool for dynorg leads and workers; prompt snippet generated from the catalog; validate-retry loop (max 2)
Verify: drive it in the browser through wails dev; golden surface renders, reload restores it, malformed output is rejected and retried.
P2
Human-in-the-loop surfaces ~1 week
  • System-generated surfaces for workflow HIL and send approvals, shown inline in chat and in the HIL drawer
  • Action router: surface id to HIL id, allowed actions, then call the existing CLI path
  • Structured questions replace free-text ask_user answers (JSON through ai_chat_answers)
Verify: approve, edit-then-approve, reject and a forged-action attempt, all against a synthetic scratch HOME with a fake HIL row.
P3
Missions ~1 week
  • Plan and report cards become system surfaces driven by the session record
  • Progress through updateDataModel so the card updates in place; budget meter component
  • Plan approval with task edits goes through existing session commands
Verify: run a mission end to end in a scratch HOME; card state matches session status at each step.
P4
Extension side panel ~1 week
  • Vanilla DOM renderer for the same catalog, honoring the no-innerHTML and URL allow-list rules in chat_render.js
  • Teach internal/extension/chat.go and chat_bridge.js the new event and action message
Verify: test bridge on port 9232 or an unshare -rn namespace, never the live bridge.
P5
Hardening and quality ~3 days
  • Accessibility attributes, keyboard flow, i18n of system surfaces
  • Small eval: how reliably each backend model emits valid surfaces (including the Jev decision providers on this branch)
  • CLI/TUI text fallback; docs in the in-app Help section
Verify: eval pass rate recorded; fallback tested headless.
